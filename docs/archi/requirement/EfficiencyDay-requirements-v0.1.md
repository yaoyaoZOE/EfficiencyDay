# EfficiencyDay 初始需求文档

- 文档版本：v0.1
- 更新日期：2026-10-19
- 文档状态：需求草案，供讨论与范围确认
- 产品定位：面向个人日常工作的计划与任务管理工具

> 本文基于最初的功能想法整理。标注为“原始需求”的内容来自原文；标注为“建议”的内容用于补齐讨论框架，尚不代表已确认的产品决策。“待确认”事项需在对应功能开发前明确。本文不限定技术栈、部署方式或交付日期。

## 1. 背景与目标

日常工作需要在长期计划、临时事项和具体执行之间切换。EfficiencyDay 希望围绕统一的工作项（WorkItem）组织这些信息，减少重复录入，并帮助用户识别优先级、安排工作和回顾完成情况。

### 1.1 产品目标

1. 将分散的工作信息整理为字段一致的工作项。
2. 通过紧急程度和重要程度构建四象限视图，辅助安排执行顺序。
3. 记录工作项的关键日期，支持按日查看与回顾。
4. 用结构化详情承载执行信息，而不只是单一描述文本。
5. 支持年度工作计划，以及不同设备之间的数据同步。
6. 通过模板、图片识别和语音录入降低任务记录成本。

### 1.2 目标用户

首要用户为管理自身日常工作和年度计划的个人使用者。团队协作、任务指派和组织权限暂不纳入本版范围。

## 2. 典型使用场景

| 场景 | 用户诉求 | 预期结果 |
| --- | --- | --- |
| 安排年度工作 | 记录全年需要完成的工作计划 | 能查看计划内容并持续跟踪进展 |
| 快速记录事项 | 在工作过程中及时记录新任务 | 生成可继续补充信息的标准化工作项 |
| 使用常用模板 | 避免重复填写相似任务的属性 | 基于模板生成任务，并按实际情况调整 |
| 从图片或语音录入 | 减少手动转录工作信息 | 先获得可核对的识别结果，再确认生成任务 |
| 决定先做什么 | 区分事项的紧急程度与重要程度 | 在四象限中查看工作项并进入详情 |
| 每日回顾 | 查看当天新增、开始、计划完成或实际完成的事项 | 按明确的日期口径归纳工作 |
| 切换设备 | 在不同设备上继续管理工作 | 在同步完成后查看一致的任务与计划信息 |

## 3. 需求范围与建议分期

以下分期仅用于讨论，不代表已确定的开发顺序。识图、语音及同步仍属于完整需求范围，不因分期被删除。

| 建议阶段 | 能力范围 | 划分理由 |
| --- | --- | --- |
| 首期：任务管理闭环 | 手动创建与编辑工作项、基础模板、四象限、关键日期、按日归纳、排序与关闭、结构化详情 | 先验证“记录—安排—执行—回顾”的核心流程 |
| 后续：计划与连续使用 | 年度工作计划、多设备同步 | 在核心任务模型明确后补齐长期规划与跨设备使用 |
| 后续：智能录入 | 图片识别生成工作项、语音生成工作项 | 依赖统一任务字段及识别结果确认流程 |

首期不主动扩展：团队协作、聊天、复杂审批、第三方日历集成、自动执行任务。是否需要提醒、重复任务和统计报表，另行讨论，不作为本版默认需求。

## 4. 工作项信息模型

原文明确提出紧急程度、目标完成日期、颜色，以及四类日期；其余字段是为了形成可讨论的任务模型而补充的建议。

| 字段 | 含义 | 来源与建议规则 |
| --- | --- | --- |
| 唯一标识 | 区分不同工作项 | 建议由系统生成，编辑和同步时保持不变 |
| 标题 | 简要说明需要完成的工作 | 建议必填 |
| 状态 | 表示当前执行阶段 | 建议为待开始、进行中、已完成、已取消，最终状态与流转规则待确认 |
| 紧急程度 | 判断事项是否紧急 | 原始需求；建议先采用紧急 / 不紧急两档 |
| 重要程度 | 判断事项是否重要 | 为四象限补充；建议先采用重要 / 不重要两档 |
| 目标完成日期（Due Date） | 希望完成工作的日期 | 原始需求；建议允许暂不填写 |
| 颜色 | 辅助视觉区分工作项 | 原始需求；含义及与四象限的关系待确认 |
| 录入日期 | 工作项首次进入系统的日期 | 原始需求；建议自动记录，不因后续编辑而改变 |
| 开始日期 | 工作实际开始的日期 | 原始需求；自动记录还是手动填写待确认 |
| 实际完成日期 | 工作实际完成的日期 | 原始需求；建议完成时记录，是否允许补录待确认 |
| 结构化详情 | 承载任务背景、执行过程和结果 | 原始需求要求超出单一描述文本，具体结构见第 5.7 节 |
| 所属年度计划 | 关联长期工作目标 | 建议字段，关联方式与是否必填待确认 |

### 4.1 日期与状态的待定规则

- “目标完成日期”表示计划，“实际完成日期”表示结果，二者不可相互覆盖。
- 建议只有“已完成”状态计入完成记录；“已取消”不等于完成。
- “关闭”是否同时包含已完成和已取消，需明确后统一用于列表、四象限和每日回顾。
- 日期是否需要精确到时间、按日归纳采用哪个时区，以及跨设备时如何保持一致，均需确认。
- 重新打开已完成任务时，原完成日期及历史记录如何保留，需在状态规则确定时一并定义。

## 5. 功能需求

### 5.1 工作项基础管理

**需求来源：** 为原有工作项相关能力补充最小操作闭环。

- 支持手动创建、查看和编辑工作项。
- 支持维护优先级、关键日期及详情信息。
- 支持按确认后的状态规则推进、完成或关闭工作项。
- 建议关闭后的工作项仍可查询和查看详情，不因关闭而自动删除。
- 无法保存或字段不合法时，应明确提示原因，并保留尚未成功保存的输入以便修正。

### 5.2 工作项模板

**需求来源：** 原始需求。

- 支持不同类型的工作项模板，减少重复填写。
- 模板至少考虑紧急程度、目标完成日期和颜色；是否包含重要程度与详情结构待确认。
- 基于模板创建的工作项应允许修改，不要求每个实例与模板完全一致。
- 建议修改模板只影响后续创建的工作项，不自动改写已有任务。
- 模板中的目标完成日期采用固定日期，还是“创建后若干天”等相对规则，待确认。
- 首期提供预置模板还是允许用户自行创建、编辑模板，待确认。

### 5.3 四象限视图

**需求来源：** 原始需求中的“四象图展示”。

| 象限 | 分类条件 | 参考含义 |
| --- | --- | --- |
| 第一象限 | 重要且紧急 | 优先处理 |
| 第二象限 | 重要但不紧急 | 规划推进 |
| 第三象限 | 不重要但紧急 | 评估处理方式 |
| 第四象限 | 不重要且不紧急 | 评估必要性 |

- 根据工作项的紧急程度和重要程度进行分类，支持从卡片进入详情。
- 建议默认展示未关闭事项，已关闭事项通过单独入口查看；最终展示规则待确认。
- 缺少分类字段的任务应有明确的待分类入口，不静默丢失，也不自动假定优先级。
- 紧急程度由用户手动指定，还是根据目标完成日期推导，待确认；不能仅凭存在截止日期就判定为紧急。
- 是否需要拖拽调整象限，不作为本版默认要求。

### 5.4 图片识别生成工作项

**需求来源：** 原始需求中的“识图生成标准化 workitem”。

- 用户提供图片后，系统提取可识别的任务信息，并映射到统一工作项字段。
- 建议流程为：提供图片 → 识别 → 核对与修改候选结果 → 确认保存。
- 图片中包含多个事项时，是否拆分为多个工作项、采用什么拆分规则，待确认。
- 无法判断的字段保持未填写并提示用户补充，不凭空生成日期或优先级。
- 识别失败或无有效内容时明确提示，允许重试或改用手动录入。
- 支持的图片格式、大小、文字语言及识别质量验收样本，需在开发前确定。

### 5.5 语音生成工作项

**需求来源：** 原始需求。

- 将语音内容转换为可编辑的文本及候选工作项。
- 建议确认保存前同时展示转写内容与提取字段，避免误识别直接进入正式任务列表。
- 对“明天”“下周”等相对日期，应展示解析后的具体日期供用户核对。
- 录音失败、权限被拒绝或无法识别时，应给出明确提示，并提供手动录入路径。
- 支持实时录音还是上传音频、识别语言及一段语音是否支持多个任务，待确认。

### 5.6 按日归纳与排序

**需求来源：** 原始需求。

- 支持按录入日期、开始日期、目标完成日期、实际完成日期查看工作项。
- 页面应明确当前使用的日期口径，不将不同日期混作同一组结果。
- 同一工作项可分别出现在不同日期口径的结果中；没有对应日期的任务不得虚构日期归组。
- 建议每日回顾分别呈现当天新增、开始、计划完成及实际完成的任务，不将其数量简单相加为独立任务总数。
- 排序需明确区分未关闭任务与已关闭任务，不能只给出笼统的“按日期排序”。

**建议排序规则，待确认后作为验收依据：**

1. 未关闭任务：目标完成日期升序，无目标完成日期的排在最后；日期相同再按录入日期升序。
2. 已完成任务：实际完成日期降序，最近完成的排在前面。
3. 其他关闭任务：单独分组，具体排序依据随关闭状态定义一并确认。

是否支持用户切换排序方式、手动排序，以及四象限内是否沿用同一规则，待确认。

### 5.7 工作项详情

**需求来源：** 原始需求明确要求“不只是简单的 description”。

建议详情分为以下信息区域，具体编辑能力与首期范围待确认：

| 区域 | 主要内容 |
| --- | --- |
| 基本信息 | 标题、状态、紧急程度、重要程度、颜色、关键日期 |
| 背景与目标 | 为什么做、希望达成什么结果 |
| 执行清单 | 将工作拆分为可勾选的步骤 |
| 过程记录 | 记录推进情况、问题与后续动作 |
| 结果与复盘 | 记录产出、结论及完成后的总结 |

暂不默认加入附件管理、多人评论或复杂富文本编辑；若确有需要，再补充格式、存储和交互要求。

### 5.8 年度工作计划

**需求来源：** 原始需求。

- 支持记录和查看指定年度的工作计划。
- 建议年度计划包含标题、所属年度、目标说明及关联工作项。
- 建议通过关联工作项跟踪执行情况，避免计划与日常任务完全割裂。
- 年度计划是否按季度或月份拆分、是否允许任务关联多个计划、跨年度任务如何处理，待确认。
- 计划进度是手动维护还是根据工作项完成情况计算，需明确后再定义计算口径。

### 5.9 多设备同步

**需求来源：** 原始需求。

- 同一用户应能在不同设备上访问同步后的工作项与年度计划。
- 建议明确展示同步中、已同步和同步失败等状态，失败时允许重试。
- 同步失败不得伪装为成功，也不得静默覆盖尚未同步的本地修改。
- 多设备同时修改同一条数据时，需要明确的冲突处理规则，不能未经确认假定“最后写入覆盖”。
- 目标设备、账号或身份识别方式、同步范围、同步触发方式及是否支持离线编辑，均待确认。
- 可接受的同步延迟与数据恢复能力需在实现该功能前约定，本文不预设数值。

### 5.10 HTML 文件的用途

**需求来源：** 原文提到“workitem 记录的 html 文件”，但未明确其角色。

需确认 HTML 文件属于以下哪类需求，再补充对应的交互和验收规则：

- 已有工作记录的数据来源，需要导入或解析。
- 工作项的导出或分享格式。
- 产品本身以 HTML 页面形式运行。

在用途明确前，不将 HTML 导入、HTML 导出或特定产品形态视为已确认范围。

## 6. 核心用户流程

### 6.1 手动记录与执行

创建工作项 → 选择模板或手动填写 → 保存 → 在列表或四象限中查看 → 补充详情并推进状态 → 完成或关闭 → 按日回顾。

### 6.2 智能录入

提供图片或语音 → 生成候选结果 → 用户核对字段与日期 → 修正或放弃 → 确认保存为工作项 → 进入统一任务管理流程。

### 6.3 年度计划跟踪

创建年度计划 → 关联工作项 → 执行工作项 → 查看关联事项及计划进展。进展计算方式以最终确认的规则为准。

## 7. 通用质量要求

- **数据可靠性：** 保存成功后重新打开仍能读取对应内容；保存失败时明确提示，不展示误导性的成功状态。
- **规则一致性：** 同一任务的状态、日期及优先级在列表、四象限、详情和每日回顾中保持一致。
- **可理解性：** 清晰区分计划日期与实际日期、完成与取消、正式任务与识别候选结果。
- **隐私：** 图片、录音和工作记录可能包含敏感信息；如需发送至外部服务，应事先明确告知并取得用户确认。
- **异常可恢复：** 识别和同步失败后应提供重试或替代路径，尽量避免用户重复录入。
- **性能与兼容性：** 支持的数据规模、设备与浏览器范围、响应时间指标在首期范围确认后补充，不以“流畅”等模糊表述作为验收标准。

## 8. 初步验收场景

以下场景用于后续细化测试；涉及建议规则的部分，须在规则确认后固化为正式验收标准。

| 编号 | 验收场景 | 预期结果 |
| --- | --- | --- |
| AC-01 | 手动创建任务，保存后重新打开 | 标题与已填写字段完整保留 |
| AC-02 | 从模板创建任务并调整字段 | 新任务采用模板默认值，同时保留用户修改 |
| AC-03 | 分别创建四种紧急 / 重要组合的任务 | 四项任务分别出现在对应象限；未分类任务有明确入口 |
| AC-04 | 修改任务优先级后切换视图 | 列表、四象限与详情展示一致 |
| AC-05 | 为任务设置四类日期，并分别按日筛选 | 每种口径仅依据对应日期返回任务，不混用计划与实际日期 |
| AC-06 | 完成或关闭任务后查看历史记录 | 任务仍可查看，并按已确认的分组及排序规则展示 |
| AC-07 | 编辑任务的结构化详情并重新打开 | 已确认纳入范围的各信息区域可独立记录且内容保留 |
| AC-08 | 识别图片或语音后修改候选结果 | 确认前不创建正式任务，确认后保存修正后的字段 |
| AC-09 | 模拟保存、识别或同步失败 | 有明确失败提示，不显示成功，并提供适用的恢复路径 |
| AC-10 | 创建年度计划并关联工作项 | 能查看关联关系，任务更新后的展示符合已确认的进展规则 |
| AC-11 | 在设备 A 修改数据，设备 B 完成同步 | 两端数据一致；冲突情形按已确认策略处理，不静默丢失修改 |

## 9. 开发前需优先确认的问题

| 优先顺序 | 待确认事项 | 影响 |
| --- | --- | --- |
| 1 | 首期范围是否采用第 3 节建议分期 | 决定首次交付边界 |
| 2 | HTML 文件的实际用途及现有样例 | 决定是否存在导入、导出或运行形态要求 |
| 3 | 优先支持的设备与使用方式 | 影响交互、数据保存及同步方案 |
| 4 | 任务状态、“关闭”的含义及重新打开规则 | 影响日期、历史记录和排序 |
| 5 | 紧急 / 重要的分级、默认值、颜色语义及排序规则 | 影响四象限与任务展示 |
| 6 | 模板维护方式及详情首期包含的区域 | 决定任务编辑能力 |
| 7 | 日期精度、时区与每日归纳方式 | 避免跨日及跨设备口径不一致 |
| 8 | 年度计划拆分、任务关联和进度口径 | 决定长期计划模型 |
| 9 | 同步身份、离线能力、冲突处理与同步指标 | 决定跨设备使用边界 |
| 10 | 识图 / 语音输入范围、外部处理授权及验收样本 | 决定智能录入的可用性与隐私边界 |

本版完成原始想法的结构化整理，不代表所有业务规则已经定稿。下一步应先确认首期范围和关键待定规则，再据此拆分开发任务。
