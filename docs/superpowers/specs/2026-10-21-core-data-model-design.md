# EfficiencyDay 核心业务数据模型设计

- 日期：2026-10-21
- 状态：设计已分段确认，待规格文档审阅
- 依据：[开发进度](../../archi/EfficiencyDay-development-progress.md)、[首期技术架构与上线时间表](../../archi/EfficiencyDay-mvp-architecture-and-schedule.md)、[初始需求](../../archi/requirement/EfficiencyDay-requirements-v0.1.md)

## 1. 目标与范围

为第一周的“登录后创建并读取工作项”纵向链路设计可迁移、可测试的核心数据模型。沿用现有 FastAPI、SQLAlchemy、Alembic、SQLite 模块化单体及健康检查行为。

本次设计覆盖：

- `users`：预置个人账号及账号时区。
- `sessions`：服务端可撤销登录会话。
- `work_items`：工作项基础字段、优先级、关键日期及结构化文本详情。
- Alembic 新迁移、首个账号初始化、最小登录与任务读写接口、数据一致性和验收测试。

执行清单、过程记录、模板、年度计划和历史事件不在本轮建表。首期不开放注册，也不加入状态事件表；重新打开后被清除的完成日期不保留为历史事件。

## 2. 方案与边界

采用分阶段的关系型核心模型：本轮只增加用户、会话、工作项三张表。与一次建立全部六张首期表相比，该方案减少本周范围和未定规则，同时保留外键、约束、版本控制及未来扩展路径。任务详情使用显式字段，不将核心字段塞进 JSON。

所有工作项都归属于用户。每次读取、修改工作项都必须同时限定当前用户和工作项 ID；顺序 ID 仅用于定位数据，不作为访问授权。

## 3. 数据模型

### 3.1 `users`

| 字段 | 设计 |
| --- | --- |
| `id` | SQLite 整数主键 |
| `username` | 必填、唯一的登录名；不要求邮箱或手机号 |
| `password_hash` | 必填的 Argon2id 密码哈希，禁止保存明文 |
| `timezone` | IANA 时区名，默认 `Asia/Shanghai` |
| `created_at` | UTC 创建时间 |

不开放公开注册。一个已存在的用户不会因后续启动时提供不同的初始化凭据而被重置。

### 3.2 `sessions`

| 字段 | 设计 |
| --- | --- |
| `id` | SQLite 整数主键 |
| `user_id` | 必填外键，指向 `users.id` |
| `token_hash` | 必填、唯一；只存高熵随机会话令牌的哈希 |
| `csrf_token` | 必填随机令牌；仅用于 CSRF 校验，不用于认证 |
| `created_at` | UTC 创建时间 |
| `expires_at` | UTC 绝对到期时间 |
| `revoked_at` | UTC 撤销时间，可空 |

会话有效期通过 `EFFICIENCYDAY_SESSION_TTL_DAYS` 配置，默认 7 天。退出登录写入 `revoked_at` 并清除 Cookie；已过期或已撤销的会话不得认证成功。浏览器会话 Cookie 使用 `HttpOnly`、`Secure`、`SameSite` 属性。`/auth/me` 只向已认证用户返回当前会话的 CSRF 令牌；客户端在每个写请求的 `X-CSRF-Token` 请求头中回传，服务端同时校验请求来源。

### 3.3 `work_items`

| 字段 | 设计 |
| --- | --- |
| `id` | SQLite 整数主键 |
| `user_id` | 必填外键，指向 `users.id` |
| `title` | 必填标题 |
| `status` | 必填状态：`pending`、`in_progress`、`completed`、`cancelled`；新建默认 `pending` |
| `is_urgent` | 可空布尔值 |
| `is_important` | 可空布尔值 |
| `color_key` | 可空预设调色板标识；颜色不参与象限计算 |
| `due_on` | 可空目标完成日，SQL `DATE` |
| `started_on` | 可空开始日，SQL `DATE` |
| `completed_on` | 可空实际完成日，SQL `DATE` |
| `background` | 可空纯文本背景 |
| `goal` | 可空纯文本目标 |
| `result` | 可空纯文本结果 |
| `reflection` | 可空纯文本复盘 |
| `version` | 必填正整数，初始值为 1，用于乐观并发控制 |
| `created_at` | 必填 UTC 创建时间 |
| `updated_at` | 必填 UTC 最近更新时间 |

数据库约束至少包括合法状态、正版本号、外键和必要的唯一性约束。`completed_on` 仅在 `status = completed` 时有值；进入其他状态时必须为空。`username`、会话令牌哈希唯一。为用户任务查询及会话失效查询建立必要索引；更细的日期索引依据后续查询与测试再添加。

SQLite 不提供带时区的原生时间戳语义；应用须统一将时间戳按 UTC 归一化并按 UTC 解释。三个工作项日历日期字段始终保存纯日期，不补造 UTC 午夜。录入日期由 `created_at` 按用户 `timezone` 转换得到，不额外复制存储。

四象限仅在紧急和重要两个字段都有明确布尔值时计算；任一字段为空即进入待分类入口。预设颜色只作为视觉标记，不代表紧急程度、重要程度或状态。

## 4. 状态和日期规则

### 4.1 状态流转

| 当前状态 | 可转入状态 |
| --- | --- |
| `pending` | `in_progress`、`completed`、`cancelled` |
| `in_progress` | `pending`、`completed`、`cancelled` |
| `completed` | `pending`、`in_progress` |
| `cancelled` | `pending`、`in_progress` |

从待开始直接完成是允许的。重新打开已完成或已取消工作项时，用户选择待开始或进行中；完成日期清空。首期只保存当前状态，不保存状态变更历史。

### 4.2 日期写入

- 第一次进入 `in_progress` 且 `started_on` 为空时，按账号时区写入当天；允许后续修正或补录。
- 从进行中退回待开始再开始时保留已有 `started_on`，表示首次开始日。
- 进入 `completed` 时按账号时区写入当天的 `completed_on`；允许修正或补录。
- 从已完成重新打开，或完成任务改为其他有效状态时清空 `completed_on`。取消状态不计入完成。
- `due_on` 只表达目标日，不自动决定紧急程度。
- 所有自动写入“当天”的业务日期均使用用户账号时区。

## 5. 首次启动与数据流

### 5.1 迁移与初始账号

1. 部署流程先备份数据库，再显式运行 Alembic 迁移；应用启动不自动改库。
2. 数据库迁移达到当前版本后，应用检查 `users` 表。
3. 若用户表为空，从受限环境变量 `EFFICIENCYDAY_INITIAL_USERNAME` 和 `EFFICIENCYDAY_INITIAL_PASSWORD` 读取唯一初始账号凭据，验证后以 Argon2id 哈希并在事务中插入。
4. 若已有账号，不以环境变量覆盖或重置账号。
5. 已迁移但用户表为空、且初始化凭据缺失或无效时，启动应显式失败，不提供成功形态的未认证替代路径。
6. 数据库未迁移或不可用时，不尝试建账号；存活检查仍可用，就绪检查按现有契约返回失败。

初始化凭据只由受限部署环境提供，不写入仓库、镜像、前端变量或日志。

### 5.2 最小 API 链路

- `POST /api/v1/auth/login`：验证用户名和密码，创建服务端会话并设置安全 Cookie。
- `GET /api/v1/auth/me`：返回当前已认证用户的基本信息、时区和当前会话 CSRF 令牌。
- `POST /api/v1/auth/logout`：撤销当前会话并清除 Cookie。
- `POST /api/v1/work-items`：在当前用户下创建工作项，返回字段与初始 `version`。
- `GET /api/v1/work-items`：只读取当前用户的工作项。
- `GET /api/v1/work-items/{id}`：仅当工作项属于当前用户时返回详情。

第一周实现创建和读取最小链路。`version` 字段从创建时即存在；后续编辑接口须使用版本条件更新，避免静默覆盖。

## 6. 错误处理与安全

- 未认证请求返回 `401`。
- 工作项不存在或不属于当前用户时统一返回 `404`，避免暴露其他用户数据是否存在。
- 请求字段校验失败返回 `422`。
- 编辑时版本不匹配返回 `409`；客户端保留本地草稿，不覆盖最新服务端数据。
- SQLite 锁等待超时返回明确可重试错误，不吞异常或报告保存成功。
- 日志不得包含密码、会话令牌、初始化凭据或工作项正文。
- 登录设置限速；所有写请求执行 CSRF 和来源校验。

## 7. 迁移与索引策略

新增 `0002` Alembic revision，创建 `users`、`sessions`、`work_items`；不修改或删除 `0001` 创建的 `app_metadata`。外键删除行为采用级联删除用户的会话和工作项。降级仅用于测试库或经过审批的维护操作，生产版本回滚不自动反向迁移。

首批索引覆盖 `sessions.user_id`、`sessions.expires_at`、`work_items.user_id` 与 `work_items(user_id, status)`。根据后续日期查询与性能证据再增补索引，不预先建立不使用的复杂索引。

## 8. 验收标准

### 本次数据模型/迁移

- 从现有 `0001` 升级到最新迁移后，`app_metadata` 保留，三个核心表及约束存在。
- 在隔离测试数据库完成升级、降级、重新升级；降级行为不作为生产应用回滚步骤。
- 外键、状态、唯一字段和正版本约束均有测试覆盖。
- 时间戳按 UTC 语义读写；工作项日期是纯日期，账号时区默认 `Asia/Shanghai`。

### 首周纵向链路

- 迁移后首次启动可使用环境配置创建一个账号；再次启动不会重复创建或更改现有密码。
- 缺少首次初始化配置时明确失败；未迁移数据库不自动执行初始化，同时存活检查仍可响应、就绪检查失败。
- 登录成功后创建工作项，刷新后仍可读取；未登录访问受保护数据被拒绝。
- 用户 A 不能读取或修改用户 B 的工作项。
- 状态、日期、待分类、会话过期/撤销及上海时区跨日规则有针对性测试。
- 后续编辑实现时，过期版本更新返回 `409` 且不覆盖已保存数据。

## 9. 明确不做

- 本次不实现代码、数据库迁移或 API。
- 不建清单、过程记录、模板、年度计划或状态事件表。
- 不做注册、邮件找回、离线编辑、自动保存或多设备实时推送。
- 不以应用启动自动运行迁移，也不因应用版本回滚自动降级数据库。
